# AI 공동개발 규칙

AI는 구현 보조 도구이며 변경의 검토와 병합 책임은 사람에게 있습니다.

## 지시 우선순위와 충돌

지시가 충돌하면 다음 순서로 판단합니다.

1. GitHub 브랜치 보호, 보안과 비밀정보 규칙
2. 현재 Issue의 승인된 범위와 완료 조건
3. `AGENTS.md`, `CONTRIBUTING.md`와 Accepted ADR
4. 현재 작업 요청
5. 기존 코드, 테스트와 스타일
6. 안전한 기본값

현재 작업 요청이 상위 규칙과 충돌하면 임의로 우회하거나 범위를 확대하지 않고 충돌 내용과 필요한 결정을 보고합니다.

## 작업 요청 기준

작업 요청에는 가능한 범위에서 목표, 현재 상태 또는 재현 방법, 완료 조건, 제약 조건, 비대상 범위와 검증 방법을 포함합니다. 정보가 부족해도 안전하고 되돌리기 쉬운 범위는 기존 패턴을 따라 진행하고, 제품 동작이나 기술 방향이 달라지는 결정은 질문하거나 `Pending`으로 남깁니다.

## Superpowers 기반 설계

- 사용자의 2026-09-25 지시에 따라, MILIMAP의 이후 설계 작업은 Superpowers를 기본으로 사용합니다. 사용자가 작업별로 명시적으로 제외한 경우는 예외입니다.
- 관련 스킬을 실제로 읽고 적용합니다. 이름이나 절차를 언급한 것만으로 플러그인을 사용했다고 보고하지 않습니다.
- `brainstorming`으로 목적, 제약, 성공 기준과 작업 크기를 먼저 정리합니다. 범위가 작은 기존 기능 변경은 대화 내 설계 승인을 받고, 구조·공용 인터페이스에 영향을 주는 작업은 문서 설계로 진행합니다.
- 구조 설계는 설계서 작성과 사용자 검토 후 `writing-plans`로 구현 계획을 만듭니다. 문서화된 계획과 실행 방식이 승인되기 전에는 구현을 시작하지 않습니다. 방향에 대한 동의를 아직 작성하지 않은 설계서·구현 계획의 승인으로 확대하지 않습니다.
- 이미 승인된 계획은 중단 지점과 최신 GitHub 상태를 확인하여 이어갑니다. 매번 설계부터 반복하거나 한 번의 승인을 다음 작업의 무제한 승인으로 취급하지 않습니다.
- 구현·수정은 해당 Superpowers 실행/TDD/검토/검증 스킬과 이 저장소의 Issue·파일 예약·승인 경계를 함께 따릅니다. 외부 라이브러리·DB·인증·API·스키마 변경은 기존의 별도 승인 원칙을 유지합니다.
- 필요한 스킬이나 실행 도구를 사용할 수 없으면 그 제한을 밝힙니다. 실행하지 않은 스킬, 독립 리뷰, 테스트를 수행했다고 주장하지 않습니다.

## 작업 시작 전

1. 최신 `dev`와 관련 Issue를 확인합니다.
2. 목표, 작업 범위, 제외 범위와 완료 조건을 확인합니다.
3. 현재 브랜치와 `git status`를 확인하고 다른 작업의 변경이 섞여 있지 않은지 확인합니다.
4. Issue의 담당자, 브랜치, 수정 예정 경로와 공용 핵심 파일 예약을 확인합니다.
5. 예상 변경 파일, 검증 방법과 위험을 먼저 정리합니다.
6. 팀에서 결정되지 않은 사항은 질문하거나 `Pending`으로 남깁니다.

동시 작업의 세부 기준은 `docs/team-workflow.md`를 따릅니다. 하나의 브랜치나 작업 폴더를 여러 Codex 작업이 공유하지 않으며, 병렬 작업은 별도 clone 또는 Git worktree를 사용합니다.

## 작업 중

- Issue 범위를 넘는 기능이나 리팩터링을 추가하지 않습니다.
- Issue에 예약되지 않은 파일이 필요하면 먼저 이유를 보고하고 예약 충돌과 병합 순서를 확인합니다.
- 공용 핵심 파일은 Issue에 지정된 통합 담당자만 수정합니다.
- 기존 파일은 먼저 읽고 필요한 부분만 수정합니다. 전체 파일을 불필요하게 다시 작성하거나 의미 없는 formatting·import 변경으로 diff를 키우지 않습니다.
- 기존 도구로 해결할 수 있는데 dependency를 추가하지 않으며, 새 dependency, 제품 아키텍처, 데이터 schema와 인증 방식을 임의로 결정하지 않습니다.
- 혜택 정보와 출처를 추측해서 생성하지 않습니다.
- API 키, 토큰, 개인 환경, 개인정보와 AI 대화 원문을 저장소에 넣지 않습니다.
- AI가 제안한 코드는 사람이 diff와 주요 동작을 직접 검토합니다.
- 충돌 시 `ours` 또는 `theirs` 전체 선택, 강제 push와 다른 브랜치 변경 삭제를 임의로 수행하지 않습니다.

## 검증과 PR

- 변경 위험에 맞춰 변경 영역의 가장 좁은 테스트나 재현 절차부터 수행하고, 필요할 때 관련 테스트·lint·빌드로 범위를 넓힙니다.
- 테스트 성공 여부는 실제 명령 결과로만 기록합니다.
- 실행하지 못했거나 환경상 생략한 검증은 가능한 정적 검토와 diff 확인으로 보완하고, 이유와 남은 위험을 명시합니다.
- PR에는 사용한 AI 도구와 범위, 사람이 검토한 부분, 알려진 위험을 기록합니다.
- 완료 보고에는 변경 파일, 실행한 검증, 실행하지 못한 검증, 위험과 후속 작업을 포함합니다.

AI 대화에서 확정된 결과는 목적에 맞게 변환합니다.

- 해야 할 일: GitHub Issue
- 중요한 기술 결정: ADR
- 구현과 검증 결과: Pull Request
- 현재 실제 상태: `docs/current-status.md`
- 반복 실행 규칙: `CONTRIBUTING.md`, `AGENTS.md` 또는 관련 docs
